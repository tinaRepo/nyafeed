# STEP27 管理者画面

## 概要

通報投稿の確認・削除ができる管理者画面を追加する。
固定パスワードによる簡易認証でアクセスを制限する。
通報一覧と全投稿一覧の2タブ構成でシンプルに実装する。

## ディレクトリ構成（差分）

```
api/
└── src/
    ├── middleware/
    │   └── adminAuth.ts          ← 新規作成（Bearer認証）
    └── routes/
        └── admin.ts              ← 新規作成

my-app/
└── src/
    ├── screens/
    │   └── AdminScreen.tsx       ← 新規作成
    └── lib/
        └── api.ts                ← 変更（admin API追加）
App.tsx                           ← 変更（admin画面遷移追加）
src/components/Footer.tsx         ← 変更（管理リンク追加）
```

---

## 環境変数

```
# api/.env
ADMIN_PASSWORD=your_strong_password_here

# my-app/.env
EXPO_PUBLIC_ADMIN_PASSWORD=your_strong_password_here
```

---

## API

### エンドポイント

| メソッド | パス               | 説明                                   |
| -------- | ------------------ | -------------------------------------- |
| GET      | `/admin/reports`   | 通報一覧（通報数・理由・投稿情報付き） |
| GET      | `/admin/posts`     | 全投稿一覧（offset/limit対応）         |
| DELETE   | `/admin/posts/:id` | 投稿を物理削除                         |

### 認証方式

```
全ルートに adminAuth ミドルウェアを適用。
Authorization: Bearer {ADMIN_PASSWORD} ヘッダーで認証する。
```

### 削除時の cascade

```
posts テーブルの削除で以下が自動削除される：
・post_reactions（cascade設定済み）
・post_reports（cascade設定済み）
```

## フロント設計

### 画面遷移

```ts
type Screen = 'feed' | 'terms' | 'privacy' | 'admin'
```

### 管理画面の構成

```
ログイン画面
    ↓ パスワード認証
管理画面
├── タブ①: 🚩 通報一覧
│   └── 通報数・理由・サムネイル・削除ボタン
└── タブ②: 📋 全投稿
    └── サムネイル・コメント・投稿日・削除ボタン
```

### 削除フロー

```
削除ボタン押下
    ↓
Alert（確認ダイアログ）
    ↓
DELETE /admin/posts/:id
    ↓
一覧からカードを即時除去（state更新）
```

# STEP28 リアクション負荷対策

## 概要

bot・自動化ツールによる大量リアクションでDB書き込みが
増えすぎないよう、1投稿あたりのリアクション上限を設ける。
上限超過時はエラーではなく現在値をそのまま返し、UXを損なわない。

## ディレクトリ構成（差分）

```
api/
└── src/
    └── routes/
        └── reactions.ts   ← 変更（上限チェック追加）
```

---

## 上限設計

```
MAX_REACTIONS_PER_POST = 10000（1投稿あたりの全リアクション合計）
```

| ケース       | 動作                                         |
| ------------ | -------------------------------------------- |
| 通常ユーザー | 上限に到達しないため影響なし                 |
| bot連打      | 10000件でDB書き込みが止まる                  |
| 上限超過時   | エラーではなく現在値を返す（UXを損なわない） |
| remove操作   | 上限チェックなし・常に削除できる             |

### レスポンスの `action` フィールド

```json
// 通常時
{ "success": true, "action": "add", "reactions": {...} }

// 上限超過時（スキップ）
{ "success": true, "action": "skipped", "reactions": {...} }
```

フロント側は `action: 'skipped'` でも正常処理するため、
ユーザーにはエラーが表示されずカウントが維持される。

---

## 処理フロー

```
POST /posts/:id/reactions（action: "add"）
    ↓
現在の合計リアクション数を取得
    ↓
>= 10000 → スキップ（現在値をそのまま返す）
< 10000  → INSERT → 最新カウントを返す

POST /posts/:id/reactions（action: "remove"）
    ↓
上限チェックなし → DELETE → 最新カウントを返す
```

---

## 動作確認チェックリスト

| 確認項目       | 期待動作                               |
| -------------- | -------------------------------------- |
| 通常利用       | 問題なくリアクションできる             |
| 上限到達時     | DB書き込みがスキップされる             |
| スキップ時のUI | エラーが表示されずカウントが維持される |
| remove操作     | 上限に関係なく削除できる               |
